# Local state

State directory precedence: `--state-dir`, `TOUKO_HOME`, `$XDG_DATA_HOME/touko`, then `$HOME/.local/share/touko`. Unix directory permissions are 0700; database, config, durable workspace and staged files are 0600. Windows permissions follow the parent directory's ACL; keep the state directory in your private user profile. A stable `.lock` uses nonblocking OS file locking; a busy operation fails instead of deleting a supposedly stale lock.

`config.json` selects a repository (`backend,branch,path,owner,name,private`) and may contain an optional `cloudflare` block (`enabled,endpoint,bucket,public_base_url`). It never stores credentials. The settings UI updates only that block: every other top-level value is kept as raw JSON, the replacement goes through a 0600 temporary file with sync/close and rename, and a disabled block keeps its target fields so toggling the mirror off and on does not discard them.

`cloudflare/credentials.json` is the optional per-workspace Cloudflare R2 pair saved by the settings UI. It is versioned, strictly decoded and bounded; the directory is 0700 and the file 0600 (also replaced atomically). This is a **plaintext** credential file whose only protection is filesystem permissions and the state-directory location; it is not an OS keychain, KMS or encrypted store, and copying or backing up the state directory copies the secret. `config.json`, the mirror ledgers, SQLite and the publication journal never contain it. A complete `TOUKO_R2_ACCESS_KEY_ID`/`TOUKO_R2_SECRET_ACCESS_KEY` pair in the process environment overrides the file wholesale for sync/upload; setting only one variable is an error rather than a mixed pair. The settings autofill lookup instead returns the saved workspace pair when present and only falls back to a complete environment pair when no file exists, so it never mixes sources. Reindex and reset leave this directory untouched. `GET /api/cloudflare/config` reports only `credentials_configured`, never the values; the separate POST-only `/api/cloudflare/credentials` autofill endpoint is the only API surface that returns them, under the same Host/Origin/CSRF and `no-store` protections. SQLite `index.db` uses schema/user_version **2**, WAL, foreign keys and one connection. It contains only rebuildable committed cache: `repository_state` (`head,tree,manifest`) and `assets`. It has no `changes` or `publication` table and no staging-base column.

`workspace.json` is the independent durable source for unpublished work: workspace `version:1`, optional `repository_id`, `base_head`, `changes`, and optional `publication` (`BaseHead,CandidateHead,CandidateTree`). Workspace version 1 is not SQLite schema 1 or repository format v1. Image payloads remain in `stage/objects/`. Preserve the full state directory when backing up unpublished work; deleting schema2 `index.db` does **not** delete stage/journal, but losing `workspace.json` or needed payloads cannot be repaired from committed Git history.

`Store.Load` joins the durable workspace with a consistent SQLite cache transaction under the Store mutex. `Save` validates both halves, commits the cache transaction **first**, then replaces the durable workspace through a 0600 temporary file and file sync/close. Unix completes the replacement with rename and destination-directory sync; Windows uses `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`, since syncing an `os.Open` directory handle is not supported there. Cache-rebuild moves use the same platform-specific operation and track files moved before a subsequent sync error so recovery can restore them. These are not one cross-resource transaction. If workspace replacement fails after cache commit, an advanced cache may coexist with the old stage/journal; that recovery evidence must remain until `sync` reconciles it. A post-rename directory-sync error on Unix is reported too; inspect/reconcile state rather than assuming rollback. `SavePublication` changes only the durable workspace and must succeed before publishing a remote ref.

## Schema1 migration and cache recovery

Opening a healthy legacy schema1 database automatically validates and durably copies its stage/base/journal to `workspace.json` **before** a SQLite transaction drops legacy tables/column and sets schema 2. An interrupted migration can resume if the two copies agree; disagreement or invalid staged data fails without deleting the legacy source. A schema1 database destroyed before this durable copy existed may contain the only unpublished records: reindex cannot invent them, and refuses unreadable legacy state. Preserve the original and recover a readable backup.

Use `touko reindex`, not manual file deletion, to recover deleted, physically corrupt, or logically invalid committed cache. This CLI path does not require `app.Open` to succeed. It acquires the workspace lock, loads durable work independently, fixes one source HEAD and verifies the complete snapshot including image bytes before rebuilding. Healthy databases are updated in place; a physically corrupt closed database and its WAL/SHM files are preserved in `index-corrupt-*` before replacement. The running Web server uses `Service.Reindex` on its existing connection rather than replacing an open database.

Reindex retains changes and publication. Stage without a journal conflicts if the source HEAD differs from its base; it is never silently rebased. A pending journal is **not resolved by reindex**: after rebuilding, run `sync` against the GitHub API recovery backend. A shallow clone cannot prove candidate ancestry or necessarily read unpublished candidate/base commits. Missing/damaged durable workspace is not treated as empty stage.

## Staging

Ingest streams a source once into a synced temporary file while computing SHA-256 and size (maximum 100,000,000 bytes); dimensions and PNG/JPEG/GIF/WebP format come from that file's header. An opt-in WebP conversion decodes PNG/JPEG, encodes a candidate, and keeps it only when its bytes are smaller; GIF and WebP inputs are stored unchanged. Staged payloads are `stage/objects/<namespace>/<hash>.<ext>`, independently of their eventual canonical/custom repository placement. Existing payloads are checked rather than overwritten. A failed batch leaves no partial staged records and releases only payloads without other staged references. Importing existing Git images stages original-path metadata, not duplicate local payloads.

First change binds staging to committed HEAD. Add/edit stays add; add/remove cancels; committed edits merge; remove after edit becomes delete. Repeated deletion is harmless; edit after staged deletion conflicts. Selectors resolve against committed IDs plus staged adds before deletion state is checked. Multi-selector removal is atomic. Tags and collections are trimmed, sorted, deduplicated and case-preserving. Read views overlay staging; they hide deletions and label records committed/added/modified.

`reset --staged` discards unpublished local changes, not remote history. With a journal it must reconcile authoritative remote relationships first (GitHub API, not shallow clone). Without a journal, GitHub CLI reset sends no HTTP requests after constructing its backend; CLI localgit still opens the selected repository, so a missing local repository can prevent reset. Web uses a lazy backend for ordinary reset.

## The local checkout and Web workspaces

For GitHub repositories, `<state-dir>/clone` is a shallow selected-branch clone (`--depth 1`), not a complete history backup. Ordinary `sync` holds the same workspace lock while it creates/updates this clone **before** reading its fixed HEAD and saving the snapshot; it requires network access. Journal recovery instead reads GitHub API relationships/candidates, then refreshes the clone after successful recovery. API writes remain the publication mechanism, not `git push`.

`verify` checks the **current local clone** without fetch; its success does not prove the latest remote branch was checked. Previews prefer local images and do not refresh the clone. Original explicit paths are read from immutable cached-tree Git blobs, not blindly from mutable checkout filenames. Missing local immutable data may require the existing API fallback; do not promise every preview works offline. A missing clone can be recreated by explicit sync; removing it never discards durable stage, but eliminates local read availability until restored.

Web routes `/w/<workspace-key>/` bind separate Server/Service instances. The existing root state remains `default`; additional repositories live under `<state-root>/workspaces/<stable-key>/`, each with its own config/cache/clone/workspace/payloads. Connecting or navigating another workspace does not replace a shared Service pointer or discard the former workspace's unpublished work. CLI selects a single state directory per invocation.

## Optional Cloudflare receipts

`cloudflare/<target-id>.json` is independent of SQLite, `workspace.json` and remote metadata. Target ID is SHA-256 of the JSON array `[normalized HTTPS endpoint,bucket]`; changing public delivery domain or credentials keeps the same receipts, while changing endpoint/bucket selects another ledger and never deletes from the old target.

Ledger version 1 stores repository/source identities and sorted entries (`key,object,etag,state,error_code?`). Only a matching `synced` entry is a receipt. `pending/failed/delete_pending/delete_failed` retain repair work; `deleted` is a lightweight tombstone. Error values are an explicit controlled-code allowlist, never network messages or credentials.

Ledger reads are strict and bounded to 64 MiB; writes use private 0700 directories, 0600 temporary files, file sync/close and the existing platform durable rename. Reindex leaves this optional directory intact. A corrupt ledger stops that target's R2 mutations but does not break GitHub publication, reset or gallery reads; the damaged file is not overwritten. Preserve a backup and restore it, or back up and move that one optional file outside the workspace before rebuilding receipts. Losing it permits current-asset backfill but cannot safely discover unknown historical orphans; TOUKO never scans or prunes a bucket to guess them.

`migration/url-mapping.csv` 与 `url-mapping.json` 由 `touko migrate paths` 写入，记录一次 URL 迁移的新旧路径和公网链接；它们不是 source of truth，可随时重新生成。
